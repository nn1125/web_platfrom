Глава 3 Реализация прототипа

В данной главе описывается реализация прототипа веб-платформы интерактивной визуализации многомерных численных алгоритмов. Рассматриваются файловая структура проекта, реализация вычислительного ядра на базе WebAssembly, организация алгоритмических модулей, компонентная архитектура пользовательского интерфейса, система интерактивной визуализации, а также механизмы темизации и маршрутизации. Реализация выполнена в соответствии с архитектурными решениями, описанными в Главе 2.

3.1 Файловая структура проекта

Проект организован в соответствии с компонентным подходом, принятым в экосистеме React. Каждый функциональный модуль вынесен в отдельный каталог, что обеспечивает наглядное разделение ответственности и упрощает навигацию по кодовой базе. Корневой каталог содержит конфигурационные файлы сборщика (Vite), манифест зависимостей (package.json) и директорию с бинарными артефактами WebAssembly.

3.2 Реализация вычислительного ядра WebAssembly

Вычислительное ядро платформы реализовано как модуль WebAssembly, скомпилированный из библиотеки OpenBLAS с помощью Emscripten SDK. Модуль предоставляет интерфейс для выполнения операций BLAS и LAPACK непосредственно в браузере, обеспечивая производительность, сопоставимую с нативными приложениями.

3.2.1 Инициализация и загрузка модуля

Загрузка WASM-модуля реализована через компонент-провайдер WasmProvider, построенный на основе React Context API. При монтировании провайдера в DOM динамически создаётся элемент <script>, загружающий файл shell_cblas.js — сгенерированный Emscripten загрузчик. Объект window.Module конфигурируется до загрузки скрипта, что позволяет задать пути к файлам, обработчики вывода и колбэк завершения инициализации:

window.Module = {
  locateFile: function(path) { return '/blas_wasm/' + path; },
  print: function(...args) { _printHandler(...args); },
  printErr: function() {},
  onRuntimeInitialized: function() {
    setWasmReady(true);
    window.Module._main(0, 0);
  }
};

Флаг loadingRef предотвращает повторную загрузку при перемонтировании компонента в режиме Strict Mode (React 19). После успешной инициализации состояние wasmReady становится истинным, и все зависимые компоненты получают доступ к вычислительному ядру через хук useWasm().

3.2.2 Интерфейс обмена данными

Для взаимодействия с WASM-ядром реализована функция runBlas, инкапсулирующая полный цикл обмена данными между JavaScript и WebAssembly. Входная команда представляет собой текстовую строку, содержащую имя BLAS/LAPACK-подпрограммы и её параметры:

const runBlas = useCallback((cmd) => {
  let output = '';
  const prev = _printHandler;
  _printHandler = (t) => { output += t + '\n'; };

  const len = window.Module.lengthBytesUTF8(cmd) + 1;
  const ptr = window.Module._malloc(len);
  window.Module.stringToUTF8(cmd, ptr, len);
  window.Module._run_command(ptr);
  window.Module._free(ptr);

  _printHandler = prev;
  return output.trim();
}, []);

Механизм обмена включает следующие этапы: (1) выделение памяти в линейном пространстве WASM-модуля через _malloc; (2) запись UTF-8-строки команды в эту память через stringToUTF8; (3) вызов экспортированной функции _run_command; (4) перехват результата через подменяемый обработчик _printHandler; (5) освобождение памяти через _free. Мутабельный обработчик _printHandler решает проблему захвата ссылки Emscripten на функцию Module.print при инициализации — последующие присвоения не имеют эффекта, поэтому перенаправление реализовано через косвенный вызов.

Результат вычислений возвращается в виде текстовой строки, которая разбирается утилитными функциями parseVec, parseMat и parseScalar из модуля solverUtils.js. Такой подход позволяет использовать единый механизм для всех типов BLAS/LAPACK-операций.

3.3 Организация алгоритмических модулей

Каждый численный метод реализован как самостоятельный модуль — JavaScript-файл, экспортирующий объект-конфигурацию. Модули распределены по трём категориям в соответствии с классификацией задач:

КатегорияКоличествоМетоды
Многомерные СЛАУ 10 Гаусс, LU, QR, Холецкого, Якоби, Зейделя, SOR, MinRes, BiCG, GMRES

3.3.1 Унифицированный интерфейс модуля

Каждый модуль экспортирует объект фиксированной структуры, содержащий метаданные и асинхронную функцию решения. Ниже приведён обобщённый шаблон:

export default {
  title: 'Название метода',
  subtitle: 'Математическое описание',
  prefix: 'url-slug',
  defaultSize: 3,
  exampleSize: 3,
  exampleA: [[...], [...], [...]],   // Пример матрицы
  exampleB: [...],                    // Пример вектора
  stepDelay: 600,                     // Задержка анимации (мс)

  async solve(ctx) {
    const { data, runBlas, viz, stepLog, skipRef } = ctx;
    // Реализация алгоритма с визуализацией
  }
};

Контекст выполнения ctx передаётся страницей-контейнером и содержит: пользовательские данные (data), функцию вызова BLAS-ядра (runBlas), ссылки на компоненты визуализации (viz) и журнала шагов (stepLog), а также флаг пропуска анимации (skipRef). Такая декомпозиция позволяет алгоритмическим модулям работать независимо от деталей пользовательского интерфейса.

3.3.2 Пример реализации: метод Гаусса

Рассмотрим реализацию метода Гаусса как характерный пример построения алгоритмического модуля. Функция solve организована в два параллельных потока выполнения: анимированный и вычислительный.

Анимированный поток отвечает за пошаговое отображение преобразований матрицы. На каждом шаге прямого хода выполняются: выбор ведущего элемента по столбцу с подсветкой кандидатов (highlightCell), перестановка строк при необходимости (highlightRow), элиминация с отображением формулы операции (setOpLabel) и покомпонентным обновлением ячеек (updateCell). Между операциями вставляются управляемые паузы через animSleep.

Вычислительный поток формирует журнал BLAS-вызовов. На каждом шаге алгоритма генерируются текстовые команды для WASM-ядра: cblas_idamax для поиска максимального элемента, cblas_dswap для перестановки строк и cblas_daxpy для элиминации. Результаты BLAS-вызовов записываются в компонент StepLog, формируя протокол вычислений. Обратная подстановка выполняется единым вызовом cblas_dtrsv, а верификация — через LAPACKE_dgesv.

Механизм пропуска анимации реализован через разделяемую ссылку skipRef. При активации пользователем все паузы мгновенно разрешаются, а матрица пересчитывается без визуальных обновлений и записывается в финальном виде.

3.3.3 Ленивая загрузка модулей

Для минимизации начального объёма загрузки применена стратегия ленивого импорта (code splitting). В корневом компоненте App.jsx каждый алгоритмический модуль зарегистрирован как фабричная функция динамического импорта:

const solverConfigs = {
  gauss:    () => import('./hooks/solvers/linear/useGauss'),
  lu:       () => import('./hooks/solvers/linear/useLU'),
  qr:       () => import('./hooks/solvers/linear/useQR'),
  // ...
};

Загрузка модуля происходит только при переходе на соответствующий маршрут. Страницы-контейнеры также загружаются лениво через React.lazy с оборачиванием в Suspense. Такой подход позволяет Vite разбивать приложение на изолированные чанки, значительно сокращая время первоначальной загрузки.

3.4 Компонентная архитектура интерфейса

Пользовательский интерфейс построен на основе библиотеки React 19 с применением функциональных компонентов и хуков. Компоненты организованы в два уровня: компоненты-страницы и переиспользуемые UI-компоненты.

3.4.1 Компоненты-страницы

В системе реализованы четыре типа страниц, каждый из которых реализует собственный сценарий работы.

HomePage — главная страница платформы. Содержит анимированную Canvas-сетку, реагирующую на движение мыши, счётчики с анимацией подсчёта и карточки навигации по категориям алгоритмов. Анимация реализована через requestAnimationFrame с физической моделью пружинного возврата узлов сетки.

AlgorithmsPage — каталог всех реализованных алгоритмов. Поддерживает фильтрацию по категориям через параметр location.state и отображение модальных окон с описаниями алгоритмов. Метаданные загружаются из централизованного реестра algorithms.js.

SolverPage — универсальная страница для решения СЛАУ. Объединяет компоненты ввода матрицы, визуализации и журнала шагов. Управление состоянием решения реализовано через useRef для императивного доступа к дочерним компонентам и useState для реактивного отслеживания процесса.

RegressionPage — страница для задач аппроксимации и регрессии. В отличие от SolverPage, реализует табличный ввод данных наблюдений с динамическим количеством признаков (от 1 до 5) и строк, а также собственную систему визуализации результатов на основе Canvas API, включающую графики рассеяния, остатков, гистограммы, корреляционные матрицы и диаграммы коэффициентов.

3.4.2 Компонент ввода данных MatrixInput

Компонент MatrixInput реализует динамический ввод матрицы A и вектора b произвольной размерности (от 1×1 до 11×11). Используется паттерн forwardRef с useImperativeHandle для экспонирования императивного API родительскому компоненту:

  • buildGrid(n) — программная генерация таблицы ввода заданной размерности;
  • readInput() — считывание и валидация всех введённых значений;
  • loadExample(A, b, n) — заполнение полей предустановленным примером.

DOM-элементы таблицы создаются императивно для обеспечения высокой производительности при частых обновлениях размерности. Каждая ячейка идентифицируется атрибутом id формата {prefix}-a-{i}-{j}, что позволяет осуществлять прямой доступ к элементам при загрузке примеров и валидации.

3.4.3 Компонент визуализации Visualization

Компонент Visualization является центральным элементом интерактивного представления алгоритма. Он предоставляет алгоритмическому модулю набор методов для управления отображением:

  • setStatus(text), setOpLabel(text) — отображение текущего шага и формулы операции;
  • setContainerHTML(html) — отрисовка интерактивной таблицы матрицы;
  • enableBacksub(runner) — активация кнопки обратной подстановки с передачей функции-анимации;
  • getSpeed() — получение текущей скорости анимации (0.25x, 0.5x, 1x).

Компонент поддерживает двухуровневую визуализацию: основную (прямой ход алгоритма) и вторичную (обратная подстановка), каждая со своим набором элементов управления. Вторичная секция монтируется по требованию и запускает анимацию через useEffect после завершения монтирования.

3.4.4 Компонент журнала шагов StepLog

Компонент StepLog отвечает за формирование протокола вычислений, воспроизводящего последовательность BLAS-вызовов. Каждый шаг содержит заголовок, текстовое описание, HTML-представление матрицы на данном этапе и BLAS-команду. Шаги добавляются через метод addStep в скрытом состоянии (класс step--hidden) и раскрываются с задержкой через showStep, создавая эффект последовательного появления. Скроллинг к последнему шагу обеспечивает навигацию в длинных протоколах.

3.5 Утилитный модуль solverUtils

Модуль solverUtils.js содержит разделяемые утилиты, используемые всеми алгоритмическими модулями. Функции модуля можно разделить на четыре группы.

Функции форматирования и разбора обеспечивают преобразование данных между JavaScript и текстовым форматом BLAS-ядра: fmtNum форматирует числа с подавлением незначащих нулей; parseVec и parseMat извлекают векторы и матрицы из текстового вывода WASM-модуля; parseScalar разбирает скалярный результат.

Функции визуализации матриц генерируют HTML-таблицы для различных представлений: renderAugmented — расширенная матрица [A|b] с выделением ведущего элемента и строк элиминации; renderMatrix — отдельная матрица с подсветкой L/U-частей; renderImat — интерактивная таблица с атрибутами data-row и data-col для покомпонентного обновления.

Функции анимации управляют интерактивным отображением: updateCell обновляет значение ячейки с CSS-анимацией перехода; highlightRow и highlightCell подсвечивают элементы цветовыми классами (imat-yellow, imat-green, imat-pivot, imat-blue); clearHighlights сбрасывает все выделения; animSleep реализует управляемую паузу, мгновенно разрешаемую при активации пропуска.

Математические функции и функции верификации: matVec, matTVec, dot, norm — базовые операции линейной алгебры на JavaScript для промежуточных вычислений; solutionHtml формирует блок результата; verifyWithDgesv выполняет независимую проверку решения через LAPACK.

3.6 Маршрутизация и навигация

Маршрутизация реализована на основе библиотеки React Router DOM v7. Корневой компонент App.jsx определяет 22 маршрута: главная страница, каталог алгоритмов и по одному маршруту на каждый из 20 алгоритмических модулей. Каждый маршрут привязан к компоненту-обёртке (SolverRoute, NonlinearRoute, RegressionRoute), который передаёт соответствующий загрузчик конфигурации в страницу-контейнер:

<Route path="/gauss" element={<SolverRoute solverKey="gauss" />} />
<Route path="/newton" element={<NonlinearRoute solverKey="newton" />} />
<Route path="/linear-regression" element={<RegressionRoute solverKey="linear-regression" />} />

Навигация между страницами осуществляется программно через хук useNavigate. Переход из главной страницы в каталог выполняется с передачей фильтра категории через объект state, что позволяет AlgorithmsPage сразу отобразить алгоритмы выбранной категории.

Компонент Header присутствует на всех страницах и содержит логотип-ссылку на главную, кнопки модальных окон «О нас» и «Контакты», а также переключатель темы. Страницы решателей дополнительно содержат кнопку «Назад к алгоритмам» для возврата в каталог.

3.7 Система визуализации результатов регрессии

Для задач аппроксимации и регрессии реализована система построения графиков на основе Canvas API без использования сторонних библиотек. Компонент RegressionPage содержит встроенный модуль рендеринга, поддерживающий шесть типов визуализаций:

  1. Карточка уравнения модели — отображает формулу регрессии и коэффициент детерминации R² с цветовой индикацией качества (зелёный ≥ 0.95, жёлтый ≥ 0.8, красный < 0.8).
  2. Метрики качества — набор карточек с числовыми показателями модели (MSE, MAE, RMSE и др.).
  3. График рассеяния с регрессионной кривой — точки наблюдений, аппроксимирующая кривая с заливкой и пунктирные линии невязок.
  4. Графики частичной зависимости (Partial Dependence) — для многомерных данных отображается влияние каждого признака на отклик при фиксации остальных.
  5. Диаграмма «Предсказанное vs Фактическое» — точки вдоль диагонали идеального предсказания.
  6. Остатки и гистограмма распределения — lollipop-диаграмма невязок и столбчатая гистограмма их распределения.

Все графики адаптированы к тёмной и светлой темам: цветовые палитры определяются динамически на основе текущего значения атрибута data-theme. Для обеспечения чёткости на экранах с высокой плотностью пикселей применяется масштабирование Canvas через devicePixelRatio.

3.8 Темизация и стилизация

Система стилей построена на CSS-переменных (Custom Properties), определённых в корневом элементе :root. Платформа поддерживает две темы — светлую (по умолчанию) и тёмную, переключаемую атрибутом data-theme="dark" на элементе <html>.

Для каждой темы определён полный набор из более чем 40 переменных, охватывающих: фоны (--bg, --bg-card), цвета текста (--text, --text-heading, --text-muted), акцентные цвета категорий (--teal, --indigo, --amber), свечения (--glow-1, --glow-2), границы и тени. Переключение темы не вызывает перерисовку React-дерева — применяются только CSS-правила. Для Canvas-визуализаций цвета темы считываются через getComputedStyle с отслеживанием изменений через MutationObserver.

Цветовая схема категорий алгоритмов обеспечивает визуальное различение: синий (teal) для СЛАУ, индиго для нелинейных систем и янтарный (amber) для задач аппроксимации. Эти цвета используются в карточках каталога, индикаторах и модальных окнах.

3.9 Конфигурация сборки

Сборка проекта выполняется с помощью Vite 8 — инструментария нового поколения, обеспечивающего мгновенную горячую перезагрузку в режиме разработки и оптимизированную production-сборку на базе Rollup.

Для корректной работы WebAssembly в браузере конфигурация Vite задаёт HTTP-заголовки изоляции: Cross-Origin-Opener-Policy: same-origin, Cross-Origin-Embedder-Policy: require-corp и Cross-Origin-Resource-Policy: same-origin. Эти заголовки необходимы для активации SharedArrayBuffer, требуемого для многопоточных вычислений в WASM.

Для обслуживания WASM-артефактов реализован кастомный плагин Vite blasWasmPlugin. В режиме разработки плагин перехватывает запросы к /blas_wasm/* и транслирует их в чтение файлов из директории blas_wasm/ с корректными MIME-типами и заголовками CORS. В режиме сборки плагин эмитирует артефакты (shell_cblas.js, shell_cblas.wasm, shell_cblas.worker.js) в каталог dist/blas_wasm/ через метод this.emitFile. Такое решение позволяет избежать дублирования файлов в public/ и обеспечивает единый источник WASM-бинарников.

Стек зависимостей проекта минимален: React 19.2, React Router DOM 7.13 и Vite 8 с плагином @vitejs/plugin-react. Отсутствие тяжёлых библиотек визуализации (D3, Chart.js) обусловлено решением реализовать графики средствами Canvas API, что снижает объём бандла и устраняет зависимость от сторонних обновлений.

3.10 Итоги реализации

В результате реализации создан прототип веб-платформы, включающий 20 алгоритмических модулей, объединённых унифицированным интерфейсом взаимодействия с WASM-ядром. Основные характеристики реализации:

  • модульная архитектура с ленивой загрузкой, обеспечивающая расширяемость и минимальное время начальной загрузки;
  • полноценная интеграция библиотеки OpenBLAS через WebAssembly с текстовым протоколом обмена данными;
  • двухуровневая система визуализации: интерактивная анимация алгоритма в реальном времени и детальный протокол BLAS-вызовов;
  • адаптивная система стилей с поддержкой тёмной и светлой тем без перемонтирования компонентов;
  • система визуализации результатов регрессии на базе Canvas API с шестью типами графиков;
  • кастомный плагин Vite для обслуживания WASM-артефактов без дублирования файлов.

Все архитектурные решения, спроектированные в Главе 2, были реализованы в полном объёме. Трёхуровневая структура (frontend, вычислительное ядро, визуализация) обеспечила разделение ответственности, а унифицированный интерфейс алгоритмических модулей позволил стандартизировать добавление новых методов.
